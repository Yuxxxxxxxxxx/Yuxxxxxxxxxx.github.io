CUDA 实现online softmax算子

一、Online Softmax 引入

传统 Safe Softmax 需要三遍扫描输入数据，而 Online Softmax 通过巧妙的数学递推，在一遍扫描中同时完成 max 和 sum 的计算，将内存读取次数从 3 次降到 2 次。

Online Softmax 的关键洞察是：max 和 sum 可以在一遍扫描中同时维护，代价只是在发现新的最大值时”修正”之前累积的 sum。

这就是 Online Softmax 的精髓——用乘法修正代替重新计算。

数学推导：

设已经处理了前 k 个元素，当前维护的状态为：

  • mk=max(x0,x1,...,xk−1) （前 k 个元素的最大值）
  • dk=∑j=0k−1exj−mk （基于当前 max 的指数和）

当处理第 k+1 个元素 xk 时：

  1. 更新最大值： mk+1=max(mk,xk)

  2. 修正已有的 sum 并加入新元素： dk+1=dk⋅emk−mk+1+exk−mk+1

    推导过程：

    dk+1=∑j=0kexj−mk+1=exk−mk+1+∑j=0k−1exj−mk+1=exk−mk+1+∑j=0k−1exj−mk⋅exj−mk+1=dk⋅emk−mk+1+exk−mk+1

关键在于 emk−mk+1 这个修正因子。如果新元素不是新的最大值（ mk+1=mk ），则 emk−mk+1=e0=1 ，修正退化为简单的累加——没有任何额外开销。

二、单线程 Online Softmax

最直接的实现：每个线程处理一行，串行地维护 (m,d) 状态，最后再做一遍归一化。

和 Safe Softmax V0 类似，单线程处理整行存在严重的并行度不足和非合并访存问题。但相比三遍扫描的 V0，这里只读了 2 遍输入数据。

注意：V0 的 Online 递推中每步都需要 expf 调用（用于修正因子），这增加了计算负担。但由于 Softmax 本身是 Memory-Bound 的，这些额外计算在高性能版本中会被内存访问延迟完全隐藏。

三、Block 级并行 + Warp Shuffle 合并规约

Online Softmax 的递推是串行的——每一步的 (m,d)(m,d) 依赖上一步。如何并行化？

关键观察：可以先让每个线程独立处理一部分元素，各自维护局部的 (mlocal,dlocal)，最后将这些局部结果合并。

两个局部结果 (m1,d1) 和 (m2,d2) 的合并公式：

mmerged=max(m1,m2)，dmerged=d1⋅em1−mmerged+d2⋅em2−mmerged

合并顺序会影响浮点精度（加法不严格满足结合律），但对于 Softmax 这种对微小误差不敏感的场景，树形规约的精度完全足够。

Online 版本的规约操作比普通 sum-reduce 复杂（每步需要 2 次 expf），但节省的内存带宽远大于多出的计算量。对于 Memory-Bound 操作，减少一次全局读取的收益是决定性的。

四、向量化加载 float4

和 Safe Softmax 的优化路径一致，使用 float4 向量化加载减少指令数。Online 递推阶段，每次加载 4 个元素，逐个更新 (m,d) 状态。

虽然 float4 一次加载 4 个元素，但 Online 递推仍然逐元素更新 (m,d)。这看似没有收益，但实际上：

  1. 内存层面：float4 加载用更少的指令传输相同的数据量，减少了指令调度的瓶颈
  2. 计算层面：4 个 expf 调用可以流水线化，编译器能更好地排布指令
  3. 整体效果：循环迭代减少 4 倍，循环开销（分支判断、地址计算）大幅降低

五、寄存器缓存消除第二遍读取

如果每行元素不多（N/blockDim≤N/blockDim≤ 几十），每个线程需要处理的元素数量有限，可以将第 1 遍读入的数据暂存在寄存器中，第 2 遍直接从寄存器取值做归一化，避免第二次全局内存读取。

这就是真正的一遍（One-Pass）Softmax——全局内存只读一次、写一次。

六、多行并行+Grid Stride

前面的版本都是”一个 Block 处理一行”、“启动 M 个 Block”。当 M 非常大（如几万行）时，会启动同等数量的 Block，带来两个问题：一是 Grid 调度开销线性增加；二是每个 Block 只跑一行就退出，Block 内的 Shared Memory 缓冲、寄存器状态都无法跨行复用。

解决方案是用 Grid Stride 让固定数量的 Block（通常按 SM 数的若干倍设置）循环覆盖所有行，并继续叠加前面的所有优化（向量化加载 + Warp Shuffle 合并规约）。V4 在算法层面与 V2 完全相同（两遍扫描），区别只在于 Block 与行的映射关系——V2 是 1:1，V4 是 1:多。

Grid Stride 并不能解决”M 很小（如 batch=1）、N 很大”导致 Block 数不足的问题——那种场景需要让多个 Block 协作处理同一行（行内分段规约 + 两段式 Kernel 或原子合并）。

当 M 很大时，Grid Stride 让 Block 循环处理多行，好处是：

  • 固定 Grid 大小避免过大的 Grid 调度开销
  • Block 内的 Shared Memory 和寄存器状态可以跨行复用
  • GPU 始终保持满载

当 M 较小时，grid_size = M，退化为 V2 的行为——每个 Block 处理一行。
