一、打开设备文件

V4L2 摄像头在 Linux 里是字符设备：

通过系统调用 open 直接打开：

  • 为什么用 O_RDWR：

常见错误：

错误 原因
No such file or directory /dev/videoN 不存在
Permission denied 当前用户不在 video 组，或 udev 权限不对
Device or resource busy 摄像头被其他进程占用

V4L2 里常见的 ioctl 命令：

命令 作用
VIDIOC_QUERYCAP 查询设备能力（是否支持 Video Capture、Metadata Capture 等）
VIDIOC_ENUM_FMT 枚举设备支持的像素格式
VIDIOC_ENUM_FRAMESIZES 枚举某格式支持的分辨率
VIDIOC_ENUM_FRAMEINTERVALS 枚举某分辨率的帧率
VIDIOC_S_FMT 设置采集格式（分辨率、像素格式）
VIDIOC_G_FMT 获取当前采集格式
VIDIOC_REQBUFS 申请缓冲区
VIDIOC_QBUF / VIDIOC_DQBUF 把缓冲区放入队列 / 从队列取出
VIDIOC_STREAMON / VIDIOC_STREAMOFF 开始 / 停止视频流

V4L2 支持三种常见 I/O。由于视频数据量大、帧率高，必须避免在用户空间和内核空间之间来回拷贝，推荐使用 MMAP：

方式 特点
read/write 简单，但通常有拷贝，不适合高性能
mmap streaming 驱动和用户态共享 buffer，V4L2 主线
userptr / dmabuf 更底层的零拷贝/跨设备共享

内核就会把这个设备的能力信息填进 cap 里。

capabilities 和 device_caps 的区别，核心在于**“物理设备” vs “当前节点”**

字段 描述对象 回答的问题
capabilities 整个物理设备 这个硬件整体能做什么？
device_caps 当前这个 /dev/videoX 节点 我现在打开的这个节点能做什么？
  • 对整个摄像头来说，它既能采集视频，也能输出元数据。所以 capabilities 会同时包含 V4L2_CAP_VIDEO_CAPTURE 和 V4L2_CAP_META_CAPTURE。
  • 但具体到某个节点：
    • video20 只能采集视频 → device_caps 只有 V4L2_CAP_VIDEO_CAPTURE
    • video21 只能采集元数据 → device_caps 只有 V4L2_CAP_META_CAPTURE

capabilities / device_caps 是位掩码，常见的有：

标志 含义
V4L2_CAP_VIDEO_CAPTURE 支持视频采集（读画面）
V4L2_CAP_VIDEO_OUTPUT 支持视频输出
V4L2_CAP_VIDEO_CAPTURE_MPLANE 支持多平面视频采集
V4L2_CAP_META_CAPTURE 支持元数据采集
V4L2_CAP_STREAMING 支持流式 I/O（mmap + 队列）
V4L2_CAP_READWRITE 支持 read()/write() 方式
V4L2_CAP_DEVICE_CAPS 表示 device_caps 字段有效

需要注意的是，通过 capabilities 是无法判断前面摄像头的两个节点（因为它们来自同一个物理设备）。要通过 device_caps 才可以判断节点是 V4L2_CAP_VIDEO_CAPTURE 还是 V4L2_CAP_META_CAPTURE。

因为老版本内核的驱动可能只填了 capabilities，没有填 device_caps。这时候如果程序直接读 device_caps，拿到的可能是 0 或者垃圾值，所以要做如下判断。

三、设置视频格式

3.1 v4l2_format

v4l2_format 是一个聚合结构体，用来描述或协商 V4L2 设备上的数据流格式。它本身不存储具体的图像参数，而是通过一个 union 容纳不同设备类型的格式定义，具体使用哪个成员由 type 字段决定。

v4l2_format 需要与 ioctl 系统调用配合使用：

命令 作用
VIDIOC_G_FMT 获取当前采集格式
VIDIOC_S_FMT 设置采集格式（分辨率、像素格式）
VIDIOC_TRY_FMT 测试格式，不实际改变设备状态

3.2 v4l2_fmtdesc

v4l2_fmtdesc 是 V4L2 里用来描述一种像素格式的结构体。它配合 VIDIOC_ENUM_FMT 这个 ioctl 使用，用来枚举设备支持的所有格式。

之前执行 v4l2-ctl --list-formats-ext 时，输出里那些 [0]: 'YUYV'、[1]: 'MJPG'、[2]: 'NV12'，就是从这个结构体读出来的。

pixelformat 是四字符编码，V4L2 用 4 个字符表示一种像素格式，通常用宏定义：

四、申请缓冲区

4.1 REQBUFS

v4l2_requestbuffers 是 V4L2 中用于申请和管理视频缓冲区的结构体。它配合 VIDIOC_REQBUFS ioctl 使用，是流式 I/O（streaming I/O）流程中必不可少的一步。

调用 VIDIOC_REQBUFS 时，驱动会尝试分配指定数量的缓冲区。驱动返回的 count 不一定等于请求值：

  • 可能更小：内存不足时。
  • 可能更大：驱动需要更多缓冲区才能正常工作。
  • 可能为 0：没有可用内存。

因此，调用后必须检查 count 的实际值，而不是假设请求的数量会被完全满足。

当 count 设为 0 时，会释放所有已分配的缓冲区，并隐含执行 VIDIOC_STREAMOFF。

VIDIOC_REQBUFS 只是完成了缓冲区的申请。之后还需要：

  1. 用 VIDIOC_QUERYBUF 查询每个缓冲区的信息
  2. 用 mmap() 将缓冲区映射到用户空间
  3. 用 VIDIOC_QBUF 将缓冲区放入队列
  4. 用 VIDIOC_STREAMON 启动视频流

如果使用 V4L2_MEMORY_MMAP，缓冲区由驱动分配在内核空间，mmap 之后应用才能直接读写。如果使用 V4L2_MEMORY_USERPTR，缓冲区由应用自己分配，这个 ioctl 只是让驱动切换到对应模式。

4.2 QUERYBUF + mmap + QBUF

v4l2_buffer 是 V4L2 流式 I/O 中单个缓冲区的“身份证”和“状态报告”。应用程序通过它告诉驱动要操作哪个缓冲区（例如 QBUF 入队），驱动则通过它告诉应用缓冲区的状态和数据信息（例如 DQBUF 出队后）。

flags 字段是缓冲区状态和属性的位掩码，常见的有：

标志 含义
V4L2_BUF_FLAG_MAPPED 缓冲区已映射到用户空间
V4L2_BUF_FLAG_QUEUED 缓冲区已在驱动队列中等待处理
V4L2_BUF_FLAG_DONE 缓冲区处理完成，应用可以取走
V4L2_BUF_FLAG_ERROR 缓冲区已就绪，但数据可能已损坏
V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC 时间戳来自 CLOCK_MONOTONIC 时钟

当 QBUF 成功时，驱动会设置 V4L2_BUF_FLAG_QUEUED 并清除 V4L2_BUF_FLAG_DONE；当 DQBUF 成功时，驱动会设置 V4L2_BUF_FLAG_DONE 并清除 V4L2_BUF_FLAG_QUEUED。
